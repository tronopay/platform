# UX-анализ личного кабинета исполнителя (`/cabinet`)

> Дата: 2026-10-11 · Область: `templates/cabinet_layout.html.twig`, `templates/cabinet/*`, `templates/login.html.twig`, `templates/register.html.twig`, `src/Controller/CabinetController.php`, `src/Form/TaskResultFormType.php`
> Метод: живой прогон сценария в headless Chrome (CDP, viewport 430×900 mobile + 1440×900 desktop) по реальному приложению на `http://localhost`, замеры геометрии/DOM/AX-дерева/контраста, скриншоты в `var/ux-shots/`.

## 1. Что проверялось и как

Сценарий исполнителя пройден целиком на реальных данных: регистрация → вход → пул → взятие задачи → страница задачи → ошибка валидации → сохранение результата → загрузка/удаление файла → модалка завершения → завершение → возврат в пул.

Инструментальные замеры (не «на глаз»):

- геометрия интерактивных элементов и тап-таргетов (44 px), горизонтальный overflow, перекрытие нижнего бара;
- контраст текста с учётом композитинга полупрозрачных фонов (`bg-opacity-10`);
- AX-дерево Chrome (доступные имена кнопок/чекбоксов, порядок фокуса);
- поведение Stimulus-счётчика, модалки, `onsubmit`-подтверждений;
- сетевой уровень (метод/enctype/статус) для формы результата.

## 2. Итоговая оценка

Каркас кабинета аккуратный и соответствует спеке: mobile-first, одна активная задача, нижняя навигация, необратимость через модалку, ленивая финализация дедлайна. Основные проблемы — не в вёрстке, а в **сценарии сдачи результата** (два места, где пользователь теряет работу или не понимает, что произошло) и в **размере тап-таргетов**.

| Область | Оценка | Коротко |
|---|---|---|
| Структура и навигация | 8/10 | Понятный поток «пул → задача», но нижний бар избыточен и без активного состояния |
| Визуальная иерархия | 8/10 | Чистые карточки, но цена/дедлайн/статус не акцентированы |
| Доступность (a11y) | 5/10 → **9/10** | ✅ доступные имена, контраст ≥ 4.5:1, `role="timer"` и `role="status"`; остаётся фокус после 422 и таймзона дат |
| Мобильная эргономика | 5/10 → **9/10** | ✅ тап-таргеты ≥ 44 px; нижний бар по-прежнему без активного состояния |
| Сдача результата | 4/10 | Потеря несохранённого текста закрыта (§3.1), лимиты файлов не показываются, размер в байтах |
| Обратная связь | 6/10 | Флеши есть и теперь анонсируются, но нет автосохранения, прогресса загрузки, статуса «на проверке» |

Оценки a11y и эргономики подняты по факту закрытия P1 (§9, пункты 4–7) — замеры до/после в §4 и §5.

## 3. Критичные находки

### 3.1 🔴 «Complete task» молча выбрасывает несохранённый текст — ✅ ИСПРАВЛЕНО

Кнопка «Complete task» — это **отдельная форма** (`_confirm_modal.html.twig`), которая POST-ит только CSRF-токен. Текст, набранный в textarea, в неё не входит.

Проверено на живом приложении (чистый прогон, сохранённый результат `SAVED-BEFORE-TYPING`):

```
saved in DB before      : SAVED-BEFORE-TYPING
textarea value at load  : SAVED-BEFORE-TYPING
textarea after typing   : UNSAVED-EDIT-typed-but-never-pressed-Save-result
modal text              : This action is irreversible. After completion the task gets
                          the status processed and the result can no longer be edited.
modal warns about unsaved text?: False
URL after confirm       : http://localhost/cabinet
flash                   : ['Task completed and submitted for review.']
DB message after        : SAVED-BEFORE-TYPING     ← набранный текст потерян
DB status after         : processed
typed text preserved?   : False
```

> **Статус: исправлено по варианту Б.** Модалка перенесена внутрь формы результата, кнопка «Complete» стала `type="submit" name="save_and_complete"`, а `submitResult` при наличии этого флага сохраняет результат и сразу вызывает `completeTask()`. Отдельный маршрут `POST /cabinet/task/{id}/complete` удалён. Тот же сценарий после правки:
>
> ```
> modal inside result form? : True
> that form's action        : /cabinet/task/01a11b14-…/result
> complete button name/value: ['save_and_complete', '1']
> modal copy                : The current result is saved and the task gets the status
>                             processed. This action is irreversible: …
> URL after confirm         : http://localhost/cabinet
> flash                     : ['Task completed and submitted for review.']
> DB status                 : processed
> DB message                : Report typed on the page, then completed without pressing Save result.
> typed text persisted?     : True
> ```
>
> Проверены и отказные пути: пустое сообщение → 422 с `is-invalid`/`aria-invalid`, задача остаётся `assigned` (пользователя больше не выбрасывает в пул); обычная «Save result» по-прежнему сохраняет черновик и оставляет задачу активной.

То же самое происходило и при отсутствии результата: «Complete task» → модалка с текстом «This action is irreversible…» → подтверждение → возврат в пул с флешем «Save a result first — completing a task requires a result.». Модалка обещала необратимость, но не говорила о том, что завершить без результата нельзя. После правки этот путь даёт 422 с ошибкой валидации прямо на странице задачи.

### 3.2 🔴 Лимиты файлов показываются после ошибки, а размер — в байтах

- В UI нет счётчика выбранных файлов: `FileType(multiple: true)` + подсказка «25 MiB each, 10 files max.» — единственное упоминание лимита, и появляется оно **до** выбора файлов. При 11-м файле пользователь получает ошибку уже после отправки (`TaskResultService::save()` кидает `RuntimeException`, ловится в контроллере во флеш).
- Размер файла выводится как `{{ file.size }} B` — без форматирования (`CabinetController::formatBytes()` был удалён вместе с чекбоксами удаления, §4.2). В списке загруженных файлов видно `26214400 B` вместо `25 MiB` — ровно на границе лимита это читается хуже всего.

**Рекомендация.** Выводить `formatBytes(file.size)` в списке; добавить Stimulus-контроллер, который считает выбранные файлы и их суммарный размер и дизейблит «Save result» при превышении (серверную валидацию оставить как есть).

### 3.3 🟠 «Return the task to the pool» удаляет черновик без явного предупреждения в UI

`TaskCabinetService::release()` удаляет все файлы результата и сам результат. Подтверждение — нативный `confirm()` с текстом «The saved result draft will be removed.», а нативный `confirm` на iOS/Android выглядит как системный диалог без контекста задачи. Плюс рядом с необратимым «Complete task» эта ссылка стоит как малозаметная `btn-link` и легко нажимается случайно.

**Рекомендация.** Переиспользовать `_confirm_modal.html.twig` (сделав его параметризуемым) для release, с явным перечислением того, что будет удалено.

## 4. Доступность

### 4.1 Иконочные кнопки без доступного имени — ✅ ИСПРАВЛЕНО

Кнопка выхода: `<button class="btn btn-sm btn-outline-secondary" title="Log out"><i class="bi bi-box-arrow-right"></i></button>` — текстового содержимого нет, только `title`. В AX-дереве Chrome она появлялась как **button без имени** (в аудите: `AX buttons: ['\uf1c3', 'Attachments (optional)', …]`, где `\uf1c3` — это приватный глиф иконки). Для скринридера это «button».

**Что сделано.** Кнопке добавлены `aria-label="Log out"` и `aria-hidden="true"` на иконке; кнопка-крестик у флешей тоже получила `aria-label="Close"`.

Замер до/после (`var/ux-shots/a11y-before.json` → `p1/a.json`):

| | До | После |
|---|---|---|
| `aria-label` | `null` | `Log out` |
| AX-имя кнопки | `'\uf1c3'` (приватный глиф) | `'Log out'` |
| Размер | 32×31 px | 44×44 px |

### 4.2 Удаление файлов: чекбокс без имени → кнопка с доступным именем — ✅ ИСПРАВЛЕНО

Первая итерация: чекбокс «Mark for removal» имел `title`, но пустой `<label class="form-check-label">`. В AX-дереве: `('', 'checkbox', None)` — **имя пустое**; пользователь скринридера не понимал, к какому файлу относится чекбокс. Тогда `aria-label="Remove {{ file.originalName }}"` добавили на сам `input`, а `title` убрали.

**Повторная правка (по замечанию заказчика).** Чекбоксы удаления заменены на кнопку-крестик `btn-outline-danger` (`role` не нужен — нативный `button`), доступное имя перенесено на неё: `aria-label="Remove {{ file.originalName }}"`; иконка `<i aria-hidden="true">`. AX-имена остались `Remove 1.txt` / `Remove dive install docker.txt` — теперь это кнопки, а не чекбоксы.

### 4.3 Контраст — ✅ ИСПРАВЛЕНО

С учётом композитинга полупрозрачных фонов (замерено, не по номиналу):

| Элемент | До | После | Требование WCAG AA |
|---|---|---|---|
| Бейдж типа задачи | **3.93:1** | 5.53:1 | 4.5:1 ✅ |
| Бейдж статуса `assigned` (`text-info`/`text-success` на 10 %-фоне) | **3.82:1** | 5.33:1 | 4.5:1 ✅ |
| Цена в TRX (`text-success`, 16px/600) | **4.53:1** | 6.45:1 | 4.5:1 ✅ |
| «Worker» в шапке (`text-secondary`, 14px) | **4.48:1** | 5.82:1 | 4.5:1 ✅ |
| Бейджи в шапке сайта («For AI agents» / «For humans») | 3.99:1 / 4.02:1 | 5.71:1 / 5.72:1 | 4.5:1 ✅ |

**Что сделано.** Вместо точечной правки каждого бейджа палитра затемнена в одной точке — на скоупе `.cabinet` переопределены `--bs-primary-rgb`, `--bs-secondary-rgb`, `--bs-success-rgb`, `--bs-info-rgb`, `--bs-secondary-color` и `--bs-link-color-rgb` (Bootstrap 5.3 выводит из них и `text-*`, и `bg-*-opacity-10`, и ссылки). Бейджи шапки сайта лежат вне `.cabinet`, поэтому для них заведён `.icon-badge-success` и убран `text-primary`/`text-success`, перебивавший цвет через `!important`.

### 4.4 Счётчик дедлайна не анонсируется — ✅ ИСПРАВЛЕНО

Блок `data-controller="countdown"` не имел `aria-live` и не был помечен как таймер; значение обновляется каждую секунду. Для скринридера это молчащий элемент. Кроме того, при `remaining <= 0` контроллер делал `window.location.reload()` — жёсткая перезагрузка (и повторные попытки, если сервер не успел финализировать).

**Что сделано.**
- `role="timer"` + `aria-live="off"` (не спамить ежесекундно) + визуально скрытая строка «Deadline 11.10.2026 21:19 UTC» — абсолютный дедлайн для скринридера.
- Сервер теперь рендерит стартовое значение `HH:MM:SS` в тот же узел, что и контроллер (`deadlineRemainingText`), — таймер виден и без JavaScript, и не «прыгает» при гидратации.
- `reload()` остался, но только на **пересечении нуля при открытой странице** и однократно. Если страница пришла уже истёкшей (сервер финализирует задачу во время рендера), перезагрузки нет вовсе — иначе при неудачной финализации получился бы бесконечный цикл.

Проверено в браузере (`p1/` и `verify_countdown.py`), три ветки контроллера:

| Ветка | Результат |
|---|---|
| A. порог 15 мин при открытой странице | `alert-warning` → `alert-danger` на `00:14:57`, перезагрузок 0 |
| B. пересечение нуля при открытой странице | ровно 1 навигация, `navigation.type === 'reload'` |
| C. страница пришла уже истёкшей | перезагрузок 0, текст `00:00:00`, класс `alert-danger` |

## 5. Мобильная эргономика — ✅ ИСПРАВЛЕНО

Замеры при viewport 430×900 (deviceScaleFactor 2):

| Элемент | До | После | Рекомендация |
|---|---|---|---|
| Кнопка «Take the task» / «Work on the task» / «Save result» / «Complete task» | высота **31–38 px** | 372×**44** px | ≥ 44 px ✅ |
| «Return the task to the pool» | 215×**31** px | 212×**44** px | ≥ 44 px ✅ |
| Кнопка удаления файла (крестик) | 24×24 (иконка) | **44×44** px (`btn btn-icon btn-outline-danger`) | ≥ 44 px ✅ |
| Кнопка выхода | **32×31** px | **44×44** px | ≥ 44 px ✅ |
| Нижний бар | 68 px | 68 px (ссылки 51 px) | оставить, но см. ниже |

**Что сделано.** В `assets/styles/app.css` на скоупе `.cabinet`: `.btn` получает `min-height: 44px` (с `inline-flex`-центровкой, чтобы иконка с текстом не разъезжались), `.btn-icon` — ещё и `min-width: 44px`; кнопка-крестик удаления файла — это `.btn.btn-icon` (44×44 px), блок `.form-check-file` под чекбоксы удалён.

Горизонтального overflow нет ни на 360, ни на 390, ни на 430, ни на 1440 — это хорошо. Перекрытия контента нижним баром **нет**: замеры на 360×640, 390×844 и 430×900 дают запас 48 px от низа последней карточки до бара.

### 5.1 Нижний бар: избыточность и отсутствие активного состояния

Бар содержит «Tasks» и «My task» и появляется **только когда есть активная задача** (`activeTaskId is defined`). При этом:

- «Tasks» ведёт на `/cabinet`, где и так висит карточка активной задачи — переход почти ничего не меняет;
- нет подсветки текущего раздела: у обоих пунктов класс `text-secondary` независимо от страницы;
- при отсутствии активной задачи бар исчезает, то есть навигация «прыгает» между состояниями.

**Рекомендация.** Либо сделать бар постоянным (пул / активная задача / выход) и подсвечивать активный пункт (`text-primary` + `fw-semibold`), либо убрать его и оставить хлебную крошку «← Back to tasks» на странице задачи. Текущий вариант даёт худшее из двух: место занимает, но не помогает ориентироваться.

## 6. Информационная архитектура и контент

1. **Пул — плоский список без сортировки и фильтров.** `TaskRepository::findPool()` сортирует по `id ASC` (то есть по UUIDv7 ≈ по времени создания), а не по цене или дедлайну. При росте пула исполнителю нечем управлять выбором. Показываются только тип, текст и цена.
2. **Локация задачи не отображается вообще.** У `Task` есть `location` (geography POINT), но ни в пуле, ни на странице задачи она не выводится — а для типов `photo`/`location`/`delivery` это ключевая информация. Показать расстояние до исполнителя нельзя (у `Worker` нет своей локации), но координаты/карту вывести стоит.
3. **`TaskType` выводится капсом в бейдже** (`{{ task.type.value|upper }}` → `DELIVERY`) — читается как аббревиатура, а не как слово. Лучше человекочитаемые подписи (`Deliver`, `Photo`, `Verify`) через словарь.
4. **Статус показывается сырым значением workflow**: `{{ task.status.value }}` → `assigned`, `processed`. Для исполнителя это внутренняя терминология; нужны подписи («In progress», «Under review»).
5. **Нет истории завершённых задач.** После завершения задача исчезает из кабинета навсегда: нет ни списка «мои завершённые», ни статуса проверки (`processed → accepted/rejected`), ни факта выплаты. Исполнитель не видит, заплатили ли ему. Это уже отмечено как открытый вопрос в `docs/ui-spec.md` §16 — по результатам анализа его стоит закрыть в первой же итерации: без обратной связи по выплате мотивация работать в пуле падает.
   > **СТАТУС: ИСПРАВЛЕНО (2026-10-12).** Добавлена вкладка «История» → `GET /cabinet/history`: список сданных задач (подписи статусов `Under review` / `Accepted` / `Rejected` / `Finished` через `TaskStatus::label()`) и сводка «Total earned» — сумма по `accepted`-задачам (деньги освобождены исполнителю). `finished` в сумму не входит: он достижим и из `accepted`, и из `rejected`, поэтому выплату не доказывает. Детали — `docs/ui-spec.md` §18.
6. **Дата в карточке результата — только в read-only виде** (`d.m.Y H:i`), без локали при `lang="en"` и без указания таймзоны.
7. **Вся копия — английская и захардкожена в Twig.** `translations/` пуст, `trans`/`|trans` в шаблонах кабинета не используются, хотя `symfony/translation` установлен, а `locale` не сконфигурирован. При этом домен продукта — русскоязычный (см. `docs/proposals.md`), и валидационные сообщения в формах уже английские. Стоит либо зафиксировать английский как единственный язык, либо завести словарь.
8. **Исполнителя не уведомляют о том, что задача вернулась в пул.** Если 2 часа истекли без результата, `TaskDeadlineFinalizer` переводит задачу в `prepaid` и очищает `assignedTo`, а в кабинете это выглядит просто как «задача исчезла»: ни флеша, ни записи в истории, ни письма/уведомления (`symfony/notifier` установлен, но не используется — в `config/packages/messenger.yaml` объявлены только маршруты `ChatMessage`/`SmsMessage`). То же при ручном `release`. Исполнитель может обнаружить пропажу только по факту.

## 7. Обратная связь и состояния

- **Нет подтверждения дедлайна при взятии задачи** кроме нативного `confirm()` в `onsubmit`. На мобильных это системный диалог с текстом «Take this task? You will have 2 hours to submit the result.» — работает, но выбивается из визуального языка и не показывает, сколько времени осталось с учётом часового пояса.
- **Нет прогресса загрузки файлов.** При 10 файлах по 25 MiB форма отправляется «молча», без индикатора; кнопки не дизейблятся, повторный клик создаёт дубль запроса.
- **Нет автосохранения черновика.** Учитывая 2-часовой дедлайн, автосохранение раз в N секунд или `beforeunload`-предупреждение заметно снизили бы риск. Острая форма проблемы (потеря текста при «Complete task») закрыта в §3.1, но перезагрузка страницы/уход со страницы по-прежнему теряет несохранённое.
- **Флеш-сообщения не имеют `role="status"`/`aria-live`** — проверено: `<div class="alert alert-success alert-dismissible fade show py-2 small">` без ролей. Скринридер их не озвучит, хотя это основная обратная связь по действиям (`Task taken.`, `Result saved.`). **✅ ИСПРАВЛЕНО:** успех/инфо получают `role="status"`, ошибки — `role="alert"` (проверено вживую: «Result saved.» → `role="status"`, «You already have an active task…» → `role="alert"`).
- **Валидационная ошибка после `submitResult` возвращает 422 с полной страницей.** Само отображение ошибки сделано правильно: Symfony рендерит `class="form-control is-invalid"`, `aria-invalid="true"` и `aria-describedby="task_result_form_message_error1"` с текстом «The result message is required.». Но **фокус после перерисовки уходит на `<body>`** — скринридер не узнает, что появилась ошибка, и пользователю с клавиатуры приходится искать поле заново. Пустой текст при этом ловится ещё на клиенте атрибутом `required` (нативная подсказка браузера), поэтому серверное сообщение пользователь увидит в основном в других случаях — превышение 5000 символов или недопустимый тип файла.
- **Дедлайн-алерт меняет цвет только при загрузке страницы.** Класс `alert-danger` вычисляется сервером по `deadlineRemaining < 900`, а Stimulus-контроллер обновляет только цифры. Проверено: при симуляции «осталось 5 минут» текст стал `00:04:58`, а класс остался `alert-warning`. То есть если пользователь открыл страницу за час до дедлайна и не перезагружал её, критическое предупреждение он не увидит. **✅ ИСПРАВЛЕНО:** контроллер сам переключает `alert-warning` ↔ `alert-danger` по тому же порогу, который сервер отдаёт в `data-countdown-urgency-threshold-value` (единый источник — переменная `urgencyThreshold` в шаблоне). Проверено: на `00:14:57` класс сменился на `alert-danger` без перезагрузки.

## 10. Технические заметки

- **Ошибка `ERR_H2_OR_QUIC_REQUIRED`.** При отправке формы результата с вложением в headless Chrome запрос падал на уровне сети (HTTP/2 → HTTP/1.1 downgrade за nginx), страница не показывала ошибку вообще. Это артефакт окружения браузера, но он вскрыл UX-пробел: **при сетевой ошибке отправки пользователь не получает никакой обратной связи** — ни сообщения, ни индикатора. Стоит добавить обработку сетевых сбоев.
- Форма результата корректно объявляет `enctype="multipart/form-data"` и `method="post"`.
- `textarea` имеет `maxlength="5000"` в HTML, но `set_value` программно это обходит — серверная валидация (`Length(max)`) отрабатывает, сообщение об ошибке рендерится. Дублирование лимита в HTML и в валидаторе корректно.
- Проверено, что удаление файла работает: кнопка-крестик → модалка подтверждения → флеш «File removed.», файл исчезает из списка (в `tests/` — целиком; вживую — `var/ux-shots/p1fix/verify_p1fix.py`, §12).
- **Как замерялся контраст.** Не по номинальным hex-значениям, а по композиту: скрипт поднимается по цепочке родителей, накладывает полупрозрачные фоны на белый и считает relative luminance. Поэтому `text-primary` на `bg-primary bg-opacity-10` даёт 3.93:1, а не «4.5+». Тот же харнесс (`var/ux-shots/audit_a11y.py`) прогнан до и после правок — baseline в `a11y-before.json`, после — в `p1/a.json`.
- **Проверка P1-правок.** `var/ux-shots/verify_p1.py` (флеши, счётчик, геометрия кнопок, модалка), `verify_p1b.py` (серверный рендер порога + успешный флеш), `verify_countdown.py` (три ветки контроллера: порог, пересечение нуля, уже истёкшая страница). Скриншоты — в `var/ux-shots/p1/`.
- Тесты: `tests/WorkerCabinetTest.php` — 16 тестов, весь набор 119 тестов / 404 assertions. Добавлены `testTaskPageExposesAccessibleCountdownAndLogout`, `testUploadingDuplicateFileNameShowsValidationError` (повторное имя → 422, текст ошибки и введённое сообщение сохраняются), `testRemoveFileViaModalConfirmation` (кнопка → модалка → `app_cabinet_remove_file` → флеш, строка и файл удалены) и переработанные проверки кнопки удаления в `testSubmitResultWithFiles`.

## 12. Правки по замечаниям заказчика (повторная загрузка файла + удаление)

Два замечания к результатам P1.

### 12.1 Повторная загрузка того же файла: 500 → понятная ошибка валидации

**Проблема.** Повторная загрузка файла с тем же именем давала **HTTP 500**: форма удаления строила массив вариантов `"имя · размер" => uuid`, два одинаковых имени схлопывались в один элемент, а шаблон индексировал `removeFiles[i]` по числу файлов → `Twig\Error\RuntimeError: Key "1" does not exist … task.html.twig line 60`. Пользователь видел ошибку сервера вместо объяснения.

**Что сделано.**
- `TaskResultFormType`: убран `removeFiles` (ChoiceType чекбоксов) и `existing_files`; добавлено `Callback`-ограничение на `files`: имя нового файла (`getClientOriginalName()`) не должно совпадать ни с одним уже прикреплённым именем результата (и с именами в той же отправке). Нарушение → **422** и текст «A file with this name is already uploaded: <имя>.», введённое сообщение в форме сохраняется.
- `TaskResultService::save()` дублирует тот же инвариант (`\RuntimeException`) — защита для вызовов вне формы.

Проверено: функциональный тест `testUploadingDuplicateFileNameShowsValidationError` (второй такой же файл → 422, сообщение сохранено, файл в результате один) + вживую (`var/ux-shots/p1fix/`, JSON-отчёт: `dup_fetch: {status: 422, showsError: true, messagePreserved: true}`).

### 12.2 Удаление файла: чекбоксы → кнопка-крестик с модалкой подтверждения

**Проблема.** Удаление файлов было чекбоксами «Mark for removal» в той же форме: пользователь должен был поставить галочку, догадаться нажать «Save result», затем снять галочку и сохранить, чтобы не потерять остальные файлы. Под списком висела подсказка «Tick the checkbox and click "Save result" to remove a file».

**Что сделано.**
- В списке файлов вместо чекбокса — кнопка-крестик `btn-outline-danger btn-icon` (44×44 px, `aria-label="Remove <имя>"`) с `data-bs-toggle="modal"` и атрибутами `data-file-remove-url/-token/-name`.
- Общая модалка `_confirm_remove_file_modal.html.twig` (вне формы результата): Stimulus-контроллер `file-remove` при `show.bs.modal` из атрибутов кнопки заполняет `action` формы, CSRF-токен и имя файла; «Remove» → POST `app_cabinet_remove_file` (`/cabinet/task/{id}/remove-file/{fileId}`) → удаление через `FileStorageInterface->delete()`, строка из БД, флеш «File removed.», перевывод страницы.
- Подсказка «Tick the checkbox…» удалена; мёртвые стили `.form-check-file` убраны.

Проверено: `testRemoveFileViaModalConfirmation` (кнопка, модалка, POST, флеш, файл физически удалён) + вживую: модалка открывается, имя/action/токен подставляются, «File removed.» появляется, строка исчезает, в БД 0 строк.

Скриншоты живой проверки: `var/ux-shots/p1fix/01-after-first-upload.png` (строка + флеш `Result saved.`), `02-duplicate-error.png`, `03-remove-modal.png` (модалка с именем файла), `04-after-remove.png` (флеш `File removed.`); `result.json` — полный протокол.

> **Артефакт окружения.** Headless Chrome в этой установке не отправляет нативные multipart-сабмиты формы, когда файлы подложены через CDP (`DOM.setFileInputFiles`): навигация упирается в `chrome-error://` и запрос не покидает браузер (urlencoded-сабмиты — логин/выход/модалка удаления — работают). Поэтому загрузки в живом прогоне делаются тем же POST'ом из JS (`fetch` + FormData + тот же CSRF-токен). Это не путь пользователя, а способ проверки: сервер видит обычный POST формы результата.
